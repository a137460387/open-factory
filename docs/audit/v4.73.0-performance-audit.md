# Open-Factory v4.73.0 Performance and Stability Audit

**Audit Date:** 2026-08-02
**Scope:** `packages/editor-core/src/`, `packages/cli/src/`, `packages/sdk/src/`
**Severity Legend:** CRITICAL > HIGH > MEDIUM > LOW > INFO

---

## 1. CRITICAL Findings

### 1.1 Export Queue cancel is state-only -- does NOT terminate the running ffmpeg process

- **File:** `packages/editor-core/src/export/export-queue.ts`, line 192-202
- **Function:** `cancelExportTask()`
- **Issue:** This function is a pure reducer on the in-memory `ExportTask[]` array. It merely sets `status: 'canceled'`. There is no wiring to kill the underlying ffmpeg child process, no AbortController reference, and no proc.kill() call.
- **Impact:** Cancelling an export task in the UI will update the UI state but the ffmpeg process continues to consume CPU, memory, and disk I/O until it terminates naturally. Multiple cancellations could accumulate orphaned ffmpeg processes, leading to resource exhaustion.
- **Recommendation:** Store an `AbortController` (or `ChildProcess` reference) on the task during `startResourceAwareExportTaskSlots` phase, and call `controller.abort()` / `proc.kill()` inside `cancelExportTask` before updating the state.

### 1.2 Headless renderer has NO abort mechanism

- **File:** `packages/editor-core/src/headless/headless-renderer.ts`, line 64-147
- **Function:** `executeFfmpegRender()`
- **Issue:** The spawned `ChildProcess` (`proc`) is never exposed to the caller. There is no AbortSignal passed in, no abort controller, and no `proc.kill()` accessible from outside the function. Once started, the render cannot be cancelled.
- **Impact:** Long-running renders (e.g., multi-hour projects) cannot be stopped. CLI users pressing Ctrl+C will kill the Node process but may leave orphaned ffmpeg subprocesses.
- **Recommendation:** Accept an `AbortSignal` parameter, attach a listener that calls `proc.kill('SIGTERM')`, and clean up temporary files on abort.

## 2. HIGH Findings

### 2.1 CLI concurrency option is accepted but not enforced for parallel rendering

- **File:** `packages/cli/src/commands/render.ts`, line 27-28, 88
- **File:** `packages/editor-core/src/headless/headless-editor-core.ts`, line 31, 152
- **Issue:** The CLI accepts `--concurrency <n>` and passes it to `HeadlessConfig`, but `executeFfmpegRender` spawns exactly one ffmpeg child process per call. The concurrency value is stored but has no operational effect -- no worker pool, no parallel subprocess spawning, no segment splitting.
- **Impact:** CLI users expecting concurrent rendering get no parallelism benefit. The setting is misleading.
- **Recommendation:** Either implement segment-based parallel rendering using the concurrency value (split work across N ffmpeg processes), or mark the option as reserved/not-yet-implemented.

### 2.2 No concurrent limits found for proxy, waveform, or thumbnail generation

- **Search scope:** `packages/editor-core/src/proxy/`, `packages/editor-core/src/audio/`, `packages/editor-core/src/timeline-thumbnails.ts`
- **Search patterns:** throttle, concurrency, semaphore, limiter
- **Issue:** No concurrency-limiting mechanism was found in proxy generation (`proxy-management.ts`), waveform rendering, or thumbnail generation code paths. These are purely in-memory data structures with no generation throttling logic. If the actual generation pipeline (e.g., ffmpeg subprocess spawning for thumbnail generation) is triggered per-asset without limits, it could flood the system.
- **Recommendation:** Add a shared concurrency limiter (e.g., a semaphore with max 2-4) for background asset processing tasks, or ensure any subprocess spawning in these paths respects the export queue's concurrency budget.

## 3. MEDIUM Findings

### 3.1 Headless project loader does full-file JSON.parse on the main/only thread

- **File:** `packages/editor-core/src/headless/headless-editor-core.ts`, line 174-176
- **Code:** `const content = await fs.readFile(projectPath, 'utf-8');` followed by `JSON.parse(content)`
- **Issue:** Project files can be large (multi-MB with many media references), and the entire file is loaded into a single string then parsed synchronously. While this is async for I/O, the `JSON.parse` call itself is synchronous and blocking.
- **Impact:** For very large project files (100MB+), `JSON.parse` can block the event loop for hundreds of milliseconds.
- **Recommendation:** Consider streaming JSON parsing (e.g., `stream-json` or incremental parsing) for large projects, or move parsing to a Worker thread.

### 3.2 Widespread main-thread JSON.parse in AI and template processing

- **Files (all under `packages/editor-core/src/`):**
  - `ai/llm-orchestrator.ts`, lines 317, 386
  - `ai/suggestion-engine.ts`, line 231
  - `ai/template-io.ts`, lines 93, 289
  - `ai-character-timeline.ts`, line 340
  - `ai-chat-editor.ts`, line 362
  - `ai-emotion-tone.ts`, line 84
  - `ai-preflight-checklist.ts`, line 247
  - `ai-sfx-match.ts`, line 118
  - `annotation-sync.ts`, line 80
  - `export/export-preset-diff.ts`, line 151
  - `export/pipeline.ts`, line 160
  - `export/preset-compatibility.ts`, line 208
  - `export/versioned-batch.ts`, line 140
  - `collaboration/collaboration.ts`, line 129
  - `collaboration/ws-transport.ts`, line 205
  - `collaboration/color-collaboration.ts`, lines 593, 624
  - `collaboration/team-management.ts`, lines 1011, 1070, 1091

  - `color-node-graph.ts`, line 367
  - `commands/timeline/utils.ts`, line 376 (fallback: `JSON.parse(JSON.stringify(value))`)
  - Plus ~15 more locations
- **Issue:** These are all synchronous `JSON.parse` calls on the main thread. While individually small, during AI inference bursts or collaboration sync events, multiple JSON.parse calls can stack up.
- **Impact:** Potential for UI jank during heavy AI processing or collaboration sync bursts.
- **Recommendation:** For the AI orchestrator path especially, consider using `structuredClone` (available in modern runtimes) or offloading large JSON parsing to a Worker. The collaboration message parsing is likely small enough to be acceptable.

### 3.3 No streaming file I/O for large inputs

- **File:** `packages/editor-core/src/headless/headless-editor-core.ts`, line 174-176
- **File:** `packages/cli/src/commands/render.ts`, entire file
- **Issue:** Project files and media data are always loaded entirely into memory. No `createReadStream`, `Readable`, or `pipeline` patterns were found for large file processing. The CLI stdin mode (`readStdinJson`) also buffers the entire stdin stream into memory.
- **Impact:** Memory pressure for projects with many assets or large project files on memory-constrained systems.
- **Recommendation:** For the headless path, use streaming where appropriate. For stdin, implement a max-size guard.

## 4. LOW Findings

### 4.1 AIWorkerPool uses inline Blob Workers -- no error recovery on individual Worker crash

- **File:** `packages/editor-core/src/ai/ai-worker.ts`, lines 312-431
- **Issue:** The `createWorkerInstance` method creates Workers from inline Blob URLs. The `worker.onerror` handler logs the error and rejects the current task, but does not attempt to recreate the crashed Worker slot. The pool size permanently shrinks by 1 on each Worker crash.
- **Impact:** Over an extended session, if Workers crash (e.g., OOM in Web Worker), the pool degrades silently.
- **Recommendation:** Add a Worker replacement strategy in `onerror`: mark the slot as idle and spawn a fresh Worker for the next task.

### 4.2 StructuredClone fallback uses double serialization

- **File:** `packages/editor-core/src/commands/timeline/utils.ts`, line 376
- **Code:** `globalThis.structuredClone ? globalThis.structuredClone(value) : (JSON.parse(JSON.stringify(value)) as T)`
- **Issue:** The fallback path does `JSON.stringify` then `JSON.parse`, which is a known performance anti-pattern for deep cloning. This is acceptable as a fallback but should not be the common path.
- **Recommendation:** Document that `structuredClone` is the expected path; the fallback exists only for ancient runtimes. No code change needed.

## 5. POSITIVE Findings (Areas Passing Audit)

### 5.1 Export queue state management is well-structured

- The export queue uses pure functional reducers operating on `ExportTask[]` arrays (`export-queue.ts`). All state transitions are explicit and testable.
- Resource-aware scheduling (`scheduling.ts`) checks memory class, effect count, and parallel eligibility before starting concurrent tasks.
- Concurrency is clamped to 1-4 via `clampExportConcurrency` (`export-queue.ts`, line 80).
- Priority-based sorting (`sortExportQueueByPriority`, line 226) uses a deterministic comparator (priority weight > createdAt > index).

### 5.2 No blocking sync filesystem calls in source code

- Zero instances of `readFileSync`, `writeFileSync`, or `existsSync` were found in any editor-core or CLI source file (all hits were in `node_modules/@types/node` type definitions).
- The headless renderer properly uses `node:fs/promises` for async I/O.

### 5.3 No `while(true)` loops found

## Summary

| Severity | Count | Theme |
|----------|-------|-------|
| CRITICAL | 2 | Export cancel not wired to process kill; headless render has no abort |
| HIGH | 2 | CLI concurrency is a no-op; no concurrency limits for proxy/waveform/thumbnail |
| MEDIUM | 3 | Main-thread JSON.parse; no streaming for large files |
| LOW | 2 | Worker crash recovery; structuredClone fallback |
| INFO/PASS | 10 | Well-structured queue, no sync FS calls, proper listener/interval/effect cleanup |

### Top 3 Action Items

1. **Wire cancel to process termination** -- `cancelExportTask` and `executeFfmpegRender` need AbortController integration so that user-initiated cancellation actually stops the ffmpeg subprocess.
2. **Implement or remove the `--concurrency` CLI option** -- Currently a misleading no-op; either implement segment-based parallel rendering or mark it as reserved.
3. **Add concurrency limits for background asset processing** -- Proxy generation, waveform rendering, and thumbnail generation should share a semaphore or use the export queue's concurrency budget to prevent resource flooding.
